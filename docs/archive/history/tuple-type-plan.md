# N-ary Tuple Type Plan

## Scope and non-scope

This plan covers adding a real **N-ary heterogeneous tuple** to Turmeric:
fixed arity, statically known element types, value semantics, with
destructuring-bind syntax.

This is a **separate effort** from `cons-in-docs-cleanup-plan.md`. The
docs cleanup uses `Vec` and does not need tuples to land. Do not block
that work on this one.

Out of scope here:
- Variadic / heterogeneous *lists* (HList in the Haskell sense). Real
  HList needs row-polymorphism or dependent typing; the value isn't
  worth the cost yet.
- Records with named fields beyond what `defstruct` already provides.
- Anonymous structural typing.

## Current state

What the language already has:

| Mechanism | Arity | Element types | Destructure? | File |
|-----------|-------|---------------|--------------|------|
| `Pair[A B]` | exactly 2 | typed A, B | via field accessors | `stdlib/pair.tur` |
| `defstruct` | N | typed, named | field accessors | language |
| `TY_SESSION_PAIR` | exactly 2 | typed | `(let [[a b] ...])` | `src/compiler/types.h:132`, `src/compiler/elab_forms.c:108` |
| `TurTuple2` (ad-hoc C struct) | 2 | `int64_t, int64_t` | via `tuple-first`/`tuple-second` | `stdlib/future.tur:569` |
| Cons list with `:int` carrier | N | erased to `:int` | head/tail | runtime |

What's missing:

- **N-ary tuple type** (`Tuple3`, `Tuple4`, ... or one variadic `Tuple[...]`)
  the type system understands as a primitive.
- **Tuple literal syntax** that doesn't require `defstruct` ceremony.
- **Generalised destructuring** beyond the SS2/SS8 session-pair case
  baked into `elab_forms.c`.

The session-pair destructure path is the key prior art: `(let [[a b] e] ...)`
is already parsed and elaborated for `TY_SESSION_PAIR`. Extending this
to a general tuple type means the syntax already exists, and the
elaborator's vector-pattern arm just needs to recognise a new type kind.

## Use cases driving this

Concrete pain points (not the docs cleanup — that's covered by `Vec`):

1. **Returning multiple typed values.** Today: nest `Pair`, define a
   one-off `defstruct`, or stuff into a `:int` cons list and lose types.
   `future-join` already invented its own `TurTuple2` rather than reuse
   `Pair`, which is a smell.
2. **Local intermediate "groupings".** `(let [(min max avg) (stats xs)] ...)`
   is one of the things readers expect from a modern typed language.
3. **Parser / lexer return shapes.** Returning `(tag span lexeme)` from
   a parse step.
4. **Pattern matching** on small fixed-shape values without inventing
   a `defstruct` for each one.

If none of these resonate in real code yet, **defer this work**. It's
an ergonomic improvement, not a correctness fix, and the cost is
non-trivial (type system, elab, codegen, runtime layout, fixtures).

## Design options

### Option A — `TupleN` as a family of generated structs

`defstruct Tuple2[A B]`, `Tuple3[A B C]`, ... up to some N (8?). Each
is a thin generated `defstruct`. Literal syntax desugars to
`(make-tuple3 a b c)`. Destructure desugars to nested `Pair`-style
field reads.

- Pros: smallest implementation. No new type kind. Reuses `defstruct`
  layout, generics, debug printing, derive-Show, all of it.
- Cons: an arbitrary cap on arity. `Tuple9` either errors or has to be
  added. Codegen sees N distinct types; type inference messages
  reference `Tuple3` rather than a tuple shape.

### Option B — `Tuple[T1 T2 ... Tn]` as a first-class variadic type

A new `Type` kind, `TY_TUPLE`, with a variable-length element array,
same as how `TY_VEC` works today.

- Pros: no arity cap. One unified runtime representation (a packed
  heap-allocated struct). Type printer says `Tuple[int float cstr]`.
  Destructuring is uniform.
- Cons: every part of the compiler that walks `Type` needs a new arm:
  printer, unifier, codegen, GADT machinery, the works. The HKT/sized
  plumbing has already done this kind of expansion; the cost is known
  but real.

### Option C — Just bless `Pair` and nesting

Document `Pair[A (Pair B C)]` as *the* way to do triples. Add a
`(tuple a b c)` macro that expands to nested pair construction, and
generalise vector destructuring (`(let [[a b c] e] ...)`) to walk
nested pairs.

- Pros: zero new type kinds. Smallest possible change.
- Cons: error messages mention `Pair`, not "tuple of three." Pair
  nesting is right-associative and observable through accessors —
  `(.snd (.snd p))` to reach the third element is bad ergonomics, and
  if any user code does that, switching to Option A or B later breaks
  them.

### Recommendation

Start with **Option A, capped at Tuple5**, generated by a
macro/template rather than handwritten. Reasons:

- Solves 95% of real cases (most multi-return is 2 or 3 values; 4 and
  5 cover the long tail without inviting `Tuple9`-shaped designs).
- Stays inside `defstruct`'s existing type-system contract.
- Leaves the door open to migrate to Option B later. A `TY_TUPLE`
  introduction would be a refactor of the runtime representation, not
  of the user-facing surface, provided we treat `Tuple2`/.../`Tuple5`
  as the public *named* types (per the Two-tuple-types answer below)
  and migration deprecates `Pair` rather than the tuple surface.

Reject Option C: nested Pair is the status quo and people already
don't reach for it.

Option B is a separate, larger effort tracked in
`docs/upcoming/tuple-variadic-type-plan.md`. Do not start it before
Option A has been in stdlib long enough to confirm the surface
syntax holds up.

## Surface design (Option A)

### Construction

```turmeric
(tuple 1 "hello" 3.14)             ; => Tuple3[int cstr float]
(tuple :ok value :unit)            ; => Tuple3[keyword T keyword]
```

`tuple` is a macro that, based on argument count, expands to
`(make-tuple<N> arg1 ... argN)`. Arity 2 routes to existing `Pair`
unless that creates a name collision — in which case keep them
distinct and let `tuple`-of-arity-2 be its own `Tuple2`.

### Destructuring

Extend the existing vector-pattern arm in `elab_forms.c` (the one
currently special-cased for `TY_SESSION_PAIR`) to handle
`Tuple2`/`Tuple3`/... structs:

```turmeric
(let [[a b c] (tuple 1 "hi" 3.14)]
  (println a))                     ; => 1
```

Mechanically: when the init value's type is a recognised `TupleN`
struct, bind each pattern symbol to the corresponding field, with the
field's declared type. Arity mismatch is a type error at the let, not
at runtime.

### Function returns

```turmeric
(defn split [s : cstr] : (Tuple2 cstr cstr)
  ...)

(let [[before after] (split "foo:bar")]
  ...)
```

Type annotation form `:(Tuple2 cstr cstr)` is just the existing typed
generic syntax — no parser change needed.

### Pattern matching

If `(match ...)` is to gain tuple patterns, that's a follow-up. Initial
landing: only `let`-with-vector-pattern. Match can use field accessors
in the interim.

## Implementation steps

1. **Spike the generator**. Write `stdlib/tuple.tur` that emits
   `Tuple2`, `Tuple3`, `Tuple4`, `Tuple5` via `defstruct` (handwritten
   if the macro layer can't yet template over arity — five copies is
   fine and the cap is firm). Each gets `tupleN-1st`, `tupleN-2nd`,
   ... accessors. Use `derive-show` so printing works. **Stop at five.**
   `Tuple6+` is the trigger to revisit Option B, not to keep
   extending the family.
2. **Add the `tuple` constructor macro**. Arity-dispatched to
   `make-tupleN`. Test 2/3/4/5; arity 1 should probably be a type
   error ("did you mean to pass the value directly?"); arity 0 may
   alias unit/`:unit`.
3. **Generalise vector destructure in `elab_forms.c`**. The existing
   `TY_SESSION_PAIR` arm becomes one case in a switch that also
   recognises tuple structs. Cleanest signal: tag the generated structs
   with a flag (e.g. `is_tuple_struct`) on their `defstruct` so the
   elaborator doesn't pattern-match on names.
4. **Replace `TurTuple2` in `stdlib/future.tur`** with the new
   `Tuple2`. Verify `future-join` still passes its fixtures. This is
   the canary user.
5. **Migrate `Pair` callers opportunistically**. Don't rip out `Pair`;
   it stays for typeclass instance reasons. But new code in stdlib
   should prefer `Tuple2` to reduce the two-tuple-types problem.
   **Status (Phase TP2): partially completed.** All stdlib internal
   ad-hoc inline-C "Pair" structs (parsec, seq, comonad, arrow) have
   been routed through the canonical `Tuple2` layout; `Eq [Tuple2]`
   ships alongside `Eq [Pair]`.  The typed `Pair[A B]` API stays
   intact for backward compatibility; new stdlib/spice code should
   prefer `Tuple2`.
6. **Fixtures**. `tests/fixtures/typed/tuple-basic/`, `tuple-destructure/`,
   `tuple-mismatch/`, `tuple-return/`. Include both the typed
   construction and destructuring paths.
7. **Docs**. One short section in `docs/guides/` introducing `tuple`.
   No README rewrites yet — the docs cleanup uses `Vec`.

## Risks and open questions

- **Two-tuple-types problem.** `Pair[A B]` and `Tuple2[A B]` are
  structurally identical but distinct nominal types. Either:
  (a) make `Tuple2` an alias for `Pair`, accepting that the field
      accessors are `.fst`/`.snd` not `.1st`/`.2nd`; or
  (b) leave them as parallel types and document `Tuple2` as the
      preferred new one.
  Option (a) is cleaner if `Pair`'s instance set (Show/Eq/Functor) is
  what users want; option (b) keeps the door open to ditching `Pair`
  later.
  **Decision: option (b).** New code targets `Tuple2`; `Pair` stays
  for back-compat and existing instance reasons but is on a
  deprecation path. Concretely:
    1. Do not delete `Pair` in this plan -- `future-join` and
       existing fixtures still depend on it.
    2. Port `Pair`'s Show/Eq/Functor instance set onto `Tuple2` as
       part of step 1, so no expressive regression vs `Pair`.
    3. New stdlib signatures use `Tuple2`. `Pair` is referenced only
       from existing call sites.
    4. A follow-up plan (out of scope here) sweeps remaining `Pair`
       users to `Tuple2` and removes `pair.tur`. That sweep is the
       gate for deciding whether Option B (variadic `TY_TUPLE`) is
       worth doing -- if `Tuple2..Tuple5` hold up in practice, the
       answer may simply be "no."
- **HKT interaction.** `Tuple2[A B]` is a binary type constructor. The
  HKT plumbing (per memory: phase S1-S8 done) should handle this, but
  verify that `Tuple2`-partial-application doesn't break the kind
  checker. Same for the higher-arity tuples.
- **Pattern-bind exhaustiveness.** The current vector-pattern code
  reads N symbols and assumes positional match. If we later want
  `(let [[a _ c] ...])` to skip the middle element, that's a separate
  affordance — Phase 2.
- **Codegen.** `defstruct` already emits an arena-allocated struct;
  no new path needed. Confirm that `derive-show` produces readable
  output (`(Tuple3 1 "hi" 3.14)` vs `(Tuple3 .1st=1 .2nd="hi" ...)`).

## Success criteria

- `(let [[a b c] (tuple 1 "x" 3.14)] (println a b c))` typechecks and
  runs.
- A function declared `:(Tuple3 int cstr float)` can be returned from
  and destructured by callers without `defstruct` boilerplate at the
  call site.
- `future-join`'s `TurTuple2` C-struct hack is gone from
  `stdlib/future.tur`.
- Type errors involving tuples say `Tuple3[int cstr float]`, not
  `Pair[int (Pair cstr float)]`.
